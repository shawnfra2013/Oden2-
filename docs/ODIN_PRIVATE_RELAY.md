# Odin private message relay — phone ↔ device

## Simple transport test (no AI key required)

The device relay recognizes exactly `/ping` as a bounded handshake. It returns
`ODIN_RELAY_PONG` with a clear statement that the reply was generated by
the Odin software without invoking inference or running shell commands.
This verifies the phone-to-Vercel-to-Odin-to-phone private message path;
it does not prove that the AI provider is available.

After safely updating Odin's Git checkout to the new reviewed `main` commit,
run the interactive helper on the device:

```bash
bash scripts/odin-relay-activate.sh
```

The helper asks for the device relay token without echo or shell history,
saves it with mode 0600, performs one authenticated poll, and starts
`odin-private-relay` under the existing Termux runit supervisor. It preserves
an existing token or runit service rather than overwriting them. On iPhone,
open the existing Odin Control app, sign in with the distinct app access
token, and send `/ping` from **Odin Device Inbox**. The status should
move through queued, delivered/read, then replied when the device is running.
AI model credentials are separately required for normal conversational turns.

Android may stop background services. These steps do not install Termux:Boot
or guarantee restoration after reboot.


The protected Odin Control iPhone app now includes a private device inbox
that can show message content, receipts and replies. This is **not** the public
GitHub diagnostic mailbox, and it is **not a direct connection to the current
ChatGPT app thread**. Messages from this thread cannot arrive automatically
without an additional ChatGPT integration.

## Architecture and security

- The existing Vercel project `odin-control` hosts `/api/relay`.
- Conversation content is stored in **private Vercel Blob storage**, never
  in public `odin-bridge-inbox` or `odin-bridge-outbox`.
- The private server-side store was provisioned for the existing project.
  Its environment configuration stays in Vercel, not GitHub.
- The phone needs the existing `ODIN_CONTROL_ACCESS_TOKEN` through the
  authenticated UI. The device uses a separate
  `ODIN_DEVICE_RELAY_TOKEN` configured in Vercel and installed privately
  in Termux at `state/odin-relay/token` (mode 0600).
- No token value belongs in source code, GitHub issues, this ChatGPT thread,
  screenshots, browser URL parameters, or a public log.
- Device-to-phone messages, device acknowledgments and phone read receipts
  use HTTPS with distinct authentication, and the server keeps a bounded
  private conversation journal. Messages are held in the store until
  displaced by newer events; old messages are not a durable backup.
- The phone polls approximately every 15 seconds while the app is open.
  The Odin client polls approximately every 45 seconds while running.
  Neither iOS push notifications nor wake-ups of an inactive ChatGPT thread
  are implemented.

## One-time pairing prerequisites

1. In Vercel, open **odin-control → Settings → Environment Variables**.
   Use a fresh unique 32+ character random value for
   `ODIN_DEVICE_RELAY_TOKEN` with target Production. Don't share it publicly.
2. Retrieve the same value securely and enter it on the Odin's Termux
   terminal without shell history. After updating the Odin checkout,
   execute:

```bash
cd ~/odin-workspace || exit 1
mkdir -p state/odin-relay
chmod 700 state/odin-relay
umask 077
read -rsp 'Private relay token: ' ODIN_RELAY_DEVICE_SECRET; echo
printf '%s\n' "$ODIN_RELAY_DEVICE_SECRET" > state/odin-relay/token
chmod 600 state/odin-relay/token
unset ODIN_RELAY_DEVICE_SECRET
python -B scripts/odin_relay_client.py --once
```

3. Enable the model provider in the local service environment. The relay
   calls `scripts/odin_chat.py`, which uses the existing local SQLite
   history and selected cloud model API. It **does not** execute returned
   code, run arbitrary shell commands, or perform unattended deployments.
4. Start `python -B scripts/odin_relay_client.py --serve` under a suitable
   existing process supervisor once one-shot pairing and inference work.
   Android battery/process management may stop background processes.

### Delivery status meanings

- `queued`: message saved in private relay; no device receipt yet.
- `delivered`: Odin poller received it.
- `read`: Odin began processing it, or the iPhone displayed a device reply.
- `replied`: a response to that message is stored.
- `failed`: Odin reported an inability to produce a model answer.

A receipt is evidence of software processing, not that a human read a
message or that a suggested command actually ran.

### Current limitation

ChatGPT can **currently** send GitHub diagnostic requests and inspect
their receipts during an active chat. It cannot autonomously subscribe
to `/api/relay`, wake a paused conversation, or become the exact same
OpenAI API session that runs in the app. The iPhone cloud AI route is a
separate OpenAI API conversation and should not be labeled as replies
from this ChatGPT app thread.

## 2026-11-19 receipt-storage recovery

- Odin `GET /api/relay` succeeded, but its `POST` delivery receipt
  returned HTTP 503; Vercel logs identified stage `odin_receipt`.
  This is a **server-side private journal write error**, not evidence
  that the physical Odin failed to poll.
- Vercel Blob kept the original private conversation in a mutable
  `odin-relay/v1/private-messages.json` journal. Acknowledgment overwrites
  continued to fail after authenticated reads succeeded. The repair
  **preserves that entire original journal unchanged** and appends future
  messages, receipts and replies as immutable private objects under
  `odin-relay/v2/events/`. No automatic migration, deletion, or replacement
  of existing conversations is performed. Reads merge legacy and new
  events, with a bounded recent-message display and explicit failure
  when the storage index cannot be read.
- The existing personal relay requires only this module; no extra storage
  service or new repository is added. Long-term high-volume retention and
  search are not yet implemented.
- The app's **Messages & responses** feed shows Odin device messages,
  iPhone messages, and cloud OpenAI API messages with source labels.
  Cloud API transcript additions are only kept in the current browser
  tab; the existing private Odin messages remain in Blob storage.
  These are **not** replies from the exact ChatGPT app thread.
- The Odin relay client records the HTTP status and method if a
  protected request fails, without printing body text or credentials.
  Existing runit supervisors must be restarted after a reviewed local
  update before the running Python process loads changed code.
- Production code, CI tests, and deployment status are separate from
  a successful phone-to-Odin `/ping` round-trip. Do not report that
  final verification as complete until a new reply is observed.

### Offline delivery and private investigations

For ordinary private messages the relay claims the original message ID
locally before execution, stores the result before network delivery, and
resends pending results on reconnect. Restart commands retain their
separate existing durable restart records. Re-submitting a new message
creates a new request ID. An interrupted ordinary execution with unknown
outcome is reported for review without executing it again.

Run `python -B scripts/odin_relay_client.py --investigations` in Termux
to list local cases, affected IDs, phases, timestamps and failure counts.
Two failures with the same action, phase and reason in one hour open one
case. An interrupted job of unknown outcome opens one immediately. Cases
remain open for review. Provider responses, tokens and raw logs are never
included in the case report. This journal covers relay and queued-worker
paths; Git sync and detached service restarts have their own logs.

For a physical delivery test, open the Stage 5 loopback page on Odin and
expand **Wi-Fi disconnect test** under System. From the private Device
Inbox send `/ping-disconnect-test` once. The saved reply has a 90-second
delivery hold. Switch Odin Wi-Fi off during the countdown and restore it
after the local monitor records a failed delivery. The server runs on the
handheld, so that monitor works offline. If local status becomes unavailable,
restore connectivity. Ordinary pings retain their usual delivery behavior.

### Hosted device inference check

Use **Chat → Odin Device Inbox → Verify Odin GPT** in a paired session. The UI sends the fixed `/ai-proof` request over the private relay and refreshes the inbox for the matching device reply. This requires the upgraded relay client, working private storage and the on-device private probe credential. Both device entry points share one attempt journal and budget.
